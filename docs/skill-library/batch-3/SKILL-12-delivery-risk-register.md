# SKILL-12 交付风险登记册

交付风险不靠一次排查会，靠一本持续更新的账：每条风险有名有姓、有触发点、有应对动作、有状态。本技能指挥 AI 以「未证实的假设」为排查轴起草风险登记册，并维护周期复查。

## 适用场景

- 项目启动建初始账、里程碑前复查、周会例行过账时；
- 出现范围漂移、资源变动、客户决策摇摆等苗头时立即补账。
不适用：已经发生并正在影响业务的事故（走故障应急响应包）；单点技术问题排查（走既有技术排障面）。

## 怎么做

1. 建账框架（本篇原创，两条轴）：交付轴——范围、时间、质量三要素里哪一条还没被证实站得住；外部轴——客户决策、第三方依赖、数据供给三类外部条件哪一条还悬着。两轴交叉出候选风险，凡「还没证实」即入账候选。
2. 逐条登记六要素（登记进项目备忘）：风险一句话／牵着哪个未证实假设／触发点（什么事件发生就该重看这条）／砸到什么（范围、时间、质量、信任至少占其一）／应对动作三选一——消掉（现在就做一件事让它不成险）、扛住（备好退路）、盯着（约定下次何时重看）／当前状态（盯注中、已消、已成险转事故）。
3. 排序在账内做：先看「更可能成险」与「砸到交付主链」的条目；排序简报由 AI 起草、蔡工定稿。不使用固定数字时限表——每条风险的复查节奏由其触发点（里程碑、外部事件）决定。
4. 复查循环：触发点到达或周会过账时，逐条问「这个假设现在证实了吗」——证实即销账并记录理由；动摇即升级应对动作；已成险的条目当天转故障应急响应包流程，账里保留指针。
5. 完成判定：候选风险全部有主有状态，无「只提风险没有应对动作」的空条目；缺输入（如第三方依赖未回复）时如实标待办，不编造缓解假象。

## 人机边界

- 风险识别建议由 AI 起草；哪条入账、哪条销账由蔡工拍板；
- 账本体登记在项目备忘（单一事实载体），不另建平行台账面；
- 不给风险打分数、不设跨项目通用阈值；对客户的表述按对内对外口径分流，未经确认不外发。
