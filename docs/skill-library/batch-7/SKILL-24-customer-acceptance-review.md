# SKILL-24 客户验收判定

交付尾段客户要一句话：这次交付到底算不算成立。本技能指挥 AI 把判定口径摊开、把承诺逐条对账、把交付物、实际使用、生意变化分三层各判各的，并把签收口径与遗留项一次说清。验收判的是客户是否认可结果成立，不是我们的流程走完了。

## 适用场景

- 合同或需求约定的一批承诺已交付，客户要求出具验收结论；
- 客户口头说过「先这样」，但结项、收款或转运维还没落，需要一次有据可查的判定；
- 上一次验收提了整改项，现在要判断能不能再次提交验收。
不适用：上线放行决策（走上线 go/no-go 决策检查）；撤场与交接（走移交撤场要点）；承诺条款怎么写（走 SLA 承诺草案）；产品缺陷的排查与修复（走技术交付速查）。

## 怎么做

1. 先定判定口径，再动手对账：用项目查询工具把合同条款清单、需求条目、会议纪要里的口头承诺收集齐，标出每条出自哪份材料、哪次沟通；口径没对齐前不逐条判定，也不催人补件。
2. 逐条对账，证据不足单列：每条承诺写状态（成立／不成立／证据不足）、判定理由、证据指针（走既有门禁证据口径：指针＋指纹，原件留工作目录）；证据不足的单列成一张待补件清单，不许折进「基本成立」或「大体可以」。
3. 分三层各给各的结论：物（交付的东西与现场是否一致、有没有残留差异）、用（客户侧实际使用者是否真的在用、卡在哪一步）、值（业务侧能观测到的变化）；一层不成立不等于整体不成立，但上一层也不许替下一层背书——东西到位不等于用起来，用起来不等于生意变了。
4. 遗留项写清三样：还差什么、谁来补、补完的判定条件是什么（写条件，不写天数与比例），并注明哪些遗留项影响「能不能结项」；影响由谁判断由人判断，AI 只列候选并标出判断人。
5. 签收口径写进结论：签字人有没有授权；没授权就记「待授权」并写清谁能授权，不把开会人在场、群里回一句「行」当成签收；AI 起草对账材料与结论草稿，人确认后再发布。
6. 结论三选一：整体成立、附条件成立（列清附带条件与条件达成前的限制）、暂不成立（列清阻断项与最小补证动作）；三选一都要写依据来源与待确认项，缺证据时只给补证动作，不宣布成立。

## 人机边界

- AI 做：收材料、逐条对账、出对账表与待补件清单、三层各写结论、起草遗留项写法与签收口径；
- 人做：确认哪份材料是承诺口径的准、判定某条算不算成立、授权与签收、遗留项是否影响结项；AI 不代客户表态、不代签、不替人判成立；
- 红线：客户真实资料只留工作目录，本仓与交付面只存指针＋指纹；
- 写入逐次确认，对外发布前由人过一遍。
