# SKILL-02 · 门禁评审怎么开

> 用途：在交付流程的阶段交界处，组织一场凭证据说话、结论可执行、记录可追溯的评审。本文只讲评审怎么组织和怎么判；**本仓系统门禁清单的唯一权威是 `server/seeds/gates.json`**，开评审前先从它取当前阶段的门槛定义，本文不复述任何清单。

## 适用场景

- 交付流程走到阶段交界处，需要正式决定「进入下一阶段、带条件继续、还是退回」；
- 某项工作成果要被正式接受进主线之前（发布、验收、对外承诺前的最后一道关）；
- 出了事故复盘之后，需要判定「可以恢复推进」还是「还欠什么证据」。

不适用：日常站会与进度同步——那是信息流动，不是判定；别把例行会开成评审会，也别把评审会开成汇报会。

## 怎么做

### 评审前（提交人自查，缺一不开会）

1. **门槛对照**：从权威清单取本阶段门槛，逐条自检，每条标注证据位置（指针＋指纹；证据原件留在工作区，材料包里只放指针，别把原件整包群发）；
2. **证据打包**：每条门槛一行——结论、证据指针、自评。自评不过的点诚实标「未达」，不包装、不藏；藏住的未达项会在会上变成信任事故；
3. **提前送达**：材料至少提前一个工作日交评审人。让评审人在会上第一次翻开材料，是提交人的失败。

### 评审中（限时，建议 30–45 分钟，超时改期不硬撑）

1. **顺序**：先过「未达」与「存疑」项，再抽查「已达」项——时间永远不够，把有限时间花在刀刃上；
2. **三态结论**：每条门槛当场记入三态之一，不许「基本可以」「差不多」式的模糊话术——
   - **放行**：证据齐、可核对、自评与复核一致；
   - **限改放行**：方向对，但列明的条件须限期补齐；逾期未补，自动视同打回，不靠人记性兜底；
   - **打回**：证据缺失或方向错误，写明缺口清单与回工入口，修复后从头再走一遍评审；
3. **书面确认**：凡涉及客户侧验收的结论，当场约定期限取得客户书面确认；口头同意不算数，邮件转发截图也算书面；
4. **纪要即时成文**：结论、条件、期限、责任人、下次复查点，五要素齐了才散会；没有纪要的评审等于没开。

### 评审后

- 放行：记录归档，进下一阶段；
- 限改放行：条件清单进跟踪账，到期复查——「条件慢慢就忘了」是门禁失效的头号方式；
- 打回：回工单循环，修复后重新评审；不允许拿「上次基本过了」当口头通行证。

### 角色纪律

提交人、评审人、拍板人三者尽量不是同一个人；提交人不得给自己拍板；拍板人只认会议记录在场的证据，会外私聊结论不进判定。

## 人机边界

AI 可以做：起草评审议程与材料包清单；逐条核对证据指针与指纹是否真实在场、是否与门槛一一对应；会议中辅助记录；会后起草纪要初稿供人修订。

人必须做：三态判定与拍板；对客户的书面确认请求与回复；接受或拒绝工作成果的最终决定。

红线：AI 不得代开评审、不得替任何角色出判定；AI 整理的证据包必须经人逐条确认后方可呈交；拍板责任永远在人。
