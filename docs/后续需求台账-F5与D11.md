## 二、D11：「交付物清单 / 交付包」设计草案（一页）

**目标**：客户结项时拿到可验证的交付包；当前 SOW/验收单的「交付物记录」章节与实际 `ProjectDocument`/`ProjectFile` 无数据关联。

**关联实体（全部复用现有表，仅加 1 张映射表）**：
- `delivery_package`：`project_id` / `status`(draft→sealed→delivered) / `sealed_at` / `sealed_by_user_id` / `manifest_sha256`
- `delivery_package_item`：`package_id` / `item_type`(document|file) / `document_version_id` / `file_version_id` / `display_name` / `sha256`（冗余存快照）
- 真相原则（A1）：清单是投影；文件本体仍在 `project_file_versions` / `project_document_versions`，包只存指针 + sha256。

**交付清单来源**：SOW 的 deliverables 字段 → 人工勾选实际版本 → 封包时逐项校验 sha256 与 status ∈ {confirmed, available}。

**版本 / sha256**：封包（seal）时冻结全部 item 指针，`manifest_sha256` = 清单 JSON 规范化哈希；任何 item 事后再出新版本不影响已封包（指针指向具体 version_id）。

**权限**：seal=项目负责人+admin；delivered（登记对外交付）=admin；查看=项目成员；下载沿用现有下载门（confirmed/archive 才可下，D4 门禁复用）。

**审计**：seal/deliver 走 `OperationEvent`（`delivery_package_sealed` / `delivery_package_delivered`），复用 D5 的交付审计模式。

**明确不做**：自动打包 zip、对外下载链接签名、与合同条款联动——留给真实客户需求出现后立项。

## 三、备忘：门禁接口对 AI 的可见性（2026-10-30）

**背景**：AI Server 助手在 api_catalog 里找不到任何 gates.\* 操作，据此向用户报告「门禁只能 UI 上点」。
实际服务端有三条门禁路由（UI 在用）：`GET /projects/<id>/gates`、`POST …/gates/<gate_key>/evidence`、
`POST …/gates/<gate_key>/decision`；它们**有意不进** ai_catalog——提交证据与人工核验拍板是门禁纪律的人工环节，
AI 不应代执行、更不应代拍板。

**遗留缺口**：AI 连门禁状态都读不到（无只读可见性），答「我的项目门禁到哪一步了」只能靠 help_fetch 查手册，
看不到项目实际进度。可选方案（二选一，均不开放写路径）：
1. `project_read` 工具的项目快照附带 gate 摘要（gate_key / status / submitted_at / decided_at）；
2. 新增只读工具 `gates_read`（capability=project.read），实现上仍走 `gate_service.list_project_gates`。

**已同步修复**（另见 PR）：内置手册 `help_manual.md` 补收「实操示例：证据文件怎么写（somwyn 样板）」整节
（此前只存在于 HelpPage.tsx，help_fetch 检索不到）、§4 补 G↔S 映射（G1↔S1…G9↔S10，源 seeds/gates.json）
与「AI 不代拍板」边界说明；并加双手册主题 parity 测试防再分叉。

**✅ 已落地（2026-10-30，用户拍板立项）**：采用方案 2——新增只读工具 `gates_read`
（capability=project.read；本地工具循环 READ_ONLY_TOOLS + DSH MCP 双路可见），
服务端 `gate_service.summarize_project_gates` 走 `list_project_gates` 瘦身：
每门 gate_key/名称/状态/拍板结论/清单 label+claim_status/accepted 计数 + 最近 5 条事件，
不含哈希与模板长文；system prompt 与手册 §4 同步提及。写路径仍不开放。
备选方案 1（快照附摘要）因 KnowledgeSnapshot 持久化 schema 波及面大而弃用。

## 七、回溯评审：PR #17（挂载认领）/ PR #18（只读确认）（2026-10-30，G5③）

参与者约定法（correctness），已合并代码的协议再核对。三条 findings 均完成「构造违反执行→驳斥」：

1. **[P2] PATCH 成功后 confirm 失败 → 前端版本分叉，重试必 409**：`GuidanceReview.save()` 只在 PATCH+confirm 双成功后才 `setDraft(next)`。违反执行：PATCH 成功（服务端 version+1）→ confirm POST 网络失败 → catch 只显错误，本地 `draft.version` 仍为旧值 → 用户再点「确认」时 PATCH 携带陈旧 version，被 `confirm_analysis` 前的乐观锁拦为 `stale_version` 409（service.py:183），循环卡死直到关面板重开。驳斥尝试（重开面板即恢复）不成立——恢复≠预防，主路径「过目即确认」在弱网下正好触发。**修复建议：PATCH 成功后立即 `setDraft(next)`，confirm 分支成功后再推进一次。**
2. **[P3] 审核面板内无旧版源警示**：`source_is_stale` 横幅只在项目卡片（ProjectGuidanceCard），GuidanceReview 面板内确认基于旧版预调研表的分析时无任何提示，服务端 `confirm_analysis` 也不校验 staleness——用户可能在面板里确认过时指引。建议：面板头部复用 stale 横幅，或 confirm 响应携带 stale 警告。
3. **[P3] 认领命名约定无服务端保障**：挂载认领靠 `display_name=预调研表`+`business_category=预调研` 精确匹配，该约定散落前端（PresurveyUploadAction）与服务端（files/service.py:209-211、312）各自字符串比较，无统一校验；已实际发生脚本上传 display_name 不符导致 ready 草稿零入口（PR #17 当时靠 ORM 数据修正救回）。建议：`set_presurvey_source` 时服务端归一化命名，或收敛为「预调研类目唯一文件」约束。

**做得对的**：PR #17 `setVersion(state ?? …)` 保住会话内上传的 autoStart 优先级；PR #18 PATCH→confirm 双乐观锁链设计正确（分叉只在错误路径处理，锁链本身无误）；两 PR 均有缺陷基线注释 + 行为钉子测试。
