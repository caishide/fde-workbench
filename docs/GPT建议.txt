## 二、我认为目前真正的瓶颈在哪里？

我认为现在有三个问题，比继续增加 Agent 更重要。

### 问题一：系统有执行能力，但缺少足够的真实交付运行数据

这是我认为当前最重要的问题。

从仓库的 P3 高级自主化立项文档看，最近一次状态检查记录：

- `agent_runs = 0`
- `workflow_runs = 0`

这意味着系统虽然已经有了相当多的执行机制，但还没有足够的真实客户项目运行数据，无法可靠判断：

- 哪些 Agent 真正有效？
- 哪些 Skill 经常失败？
- 哪些 Workflow 节点需要人工干预？
- 哪些任务可以安全自动化？
- Agent 是否真正节省了工程师时间？

因此，下一步最应该做的不是继续扩展自主化，而是让系统进入真实项目试运行。

建议：选择一个制造业客户交付场景，跑出第一批完整的真实 Workflow Run。

### 问题二：Agent 的执行能力与 FDE 交付过程还没有完全形成自动闭环

目前有 Agent、Skill、Workflow、产物和人工接受机制，但还需要进一步打通：

客户材料 → 业务事实 → 本体 → 流程 → 实施任务 → Agent 执行 → 测试 → 验收 → 交付。

尤其要让每个阶段的输出成为下一阶段可直接消费的结构化输入，而不是让工程师不断复制粘贴文档、重新向 Agent 解释上下文。

### 问题三：缺少足够完整的交付结果评价体系

现有 Agent 产物接受记录是一个很好的起点。

但真正的 FDE 交付智能化，需要衡量的不只是 Agent 是否完成任务，还包括：

- 工程师修改了多少；
- 交付任务返工几次；
- 生成的方案是否被采用；
- 测试是否一次通过；
- 客户是否验收；
- 实际花费多少时间；
- 最终节省了多少人工工作。

否则系统会越来越会生成内容，却无法证明交付效率真的提升。

## 四、我最建议优先打通的一个场景

考虑到你的主要目标是服务制造业 SMEs，我建议不要先做一个覆盖所有行业的通用 Agent。

先把一个典型制造业客户的 FDE 交付流程跑通：

## 制造业客户 FDE 自动交付闭环

1. 客户资料导入

   上传企业介绍、产品资料、组织结构、现有 SOP、系统截图等。
2. AI 客户访谈

   转写访谈、整理纪要、自动追问缺失信息。
3. 业务本体构建

   识别客户、订单、产品、生产、库存、报价、发货、售后等对象。
4. 业务流程分析

   识别现有流程、人工操作、系统断点和自动化机会。
5. 解决方案生成

   生成目标流程、系统架构、技术选型、投资预算和实施计划。
6. 实施任务自动拆解

   生成 Workflow、Agent、Skill 和工程任务草稿。
7. AI 工程实施

   调用编码 Agent、自动化工具和 API 执行获批任务。
8. 自动测试与验收

   生成测试报告、证据链和未完成事项。
9. 交付与经验沉淀

   生成交付文档、客户培训材料和可复用 Skill 候选。

这里要特别强调：客户确认、方案批准、外部写入、发信、付款等操作仍然保留人工授权。你现在的安全设计是正确方向，不建议为了自动化率牺牲它。

## 五、近期最值得处理的技术问题：ZCode 执行通道

最新提交 `7368094` 有一个很值得关注的进展：

新增 `server/src/fde_api/agents/zcode_contract.py`，已经实现：

- 真实 CLI 参数构造；
- `--resume` 会话续接参数；

- CLI 汇总结果到 Agent 事件的映射；
- 测试夹具和契约测试。

但它目前是纯函数契约层，没有真正 spawn ZCode，也没有接通宿主代理。

当前方案已经确定走 A：Windows 宿主侧代理，而不是让 Linux Docker 容器直接运行宿主 CLI。

我建议下一步严格按照现有台账推进：

1. 取得 ZCode 商用条款书面确认。
2. 完成宿主代理的最小安全执行闭环。
3. 明确代理只服务于已授权的单次 Agent Run。
4. 验证会话续接、产物指针、超时和终止回收。
5. 进行真实机器联调和授权签核。
6. 先在脱敏项目中试运行。

目前 `adapter_missing` 仍然维持是合理的，不应为了让界面显示“已连接”而提前放开执行。

- 需求到方案的耗时；
- 方案到实施任务的转化率；
- 自动测试一次通过率；
- 每个交付阶段的返工率；
- 每个项目节省的人工工时。

## 七、最终建议：现在不要急着开发更多功能

我认为你的 Workbench 已经到了一个重要转折点：

从“把 FDE 工作流程数字化”，转向“让 AI 真正承担 FDE 交付中的可验证工作”。

现在应该优先验证三个闭环：

1. 访谈 → 本体 → 业务方案：AI 能不能真正理解客户业务？
2. 方案 → Workflow → Agent 执行：AI 能不能真正完成工程任务？
3. 执行 → 测试 → 人工验收 → Skill 沉淀：AI 能不能持续提高下一次交付效率？

这三个闭环比再引入一个多 Agent 框架更有价值。

我的建议是先启动一个独立的 `goal-v3.1` 迭代，优先做真实试点，不要马上启动大规模架构重构。
