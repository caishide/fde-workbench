## 0. 一页结论

1. **「四类主体同时在线工作」= 评估文档的 B 路线（单实例多主体隔离）+ G 线商业语义（角色/权益/额度/席位/商机/区域）的组合**。评估文档已给出工程下限：**15～30×、660+ 必判点位**——这是本文全部排期的锚。
2. 但 B 不是一天建成的。本文把 B 拆成 **M0–M8 九个 Goal**（§7），每轮一个可独立验收的切片，**首个可验收切片（M1 主体与组织底座）约 3–5 天**即可让「两个企业各自登录、各自看各自的项目」跑起来；全量商用态（含计费、商机、区域）约 **35–55 个工作日**（甲路线估算，见 §6——**该数须 M0 盘点后校准**，若 `OWNER` 选乙路线则回到 15–30× 区间）。
3. **本文不预设技术路线为「全量 tenant_id + RLS」**。评估文档的 15～30× 按「130 表全量租户化」测算；而 G 线任务书 G6 已裁决「企业空间**复用 `projects` 权限模型与 `add_project_member`，不新建平行权限体系」**——项目域 67 张表可经「组织归属 + 既有成员隔离」覆盖，真正的硬骨头是 **63 张全局共享表里的 122 个写端点** 与 **12 个无前缀 Redis 键族**。甲（组织级隔离复用既有模型）与乙（全量 tenant_id + RLS）的选择是 **§11 第一拍板点**，本文按甲编写、乙作为规模化演进保留。
4. **AI 供应商合规红线自动升级**：评估文档 §7.0 已实证「GLM/MiniMax 订阅 key 明文不适用于自建 SaaS」——多客户商用后平台即 SaaS，**模型侧只允许按量付费 key**，且预算闸须从「整实例一个数」改为「按主体分别设额」（GAP-04 的额度账承担）。此项进 M4。
5. **顺序纪律沿用 G 线**：M0（决策与盘点，零代码）→ M1（底座）→ M2/M3/M4（可部分并行，各自独立切片）→ M5–M7（商业语义落地）→ M8（回归与试点）。每轮 DoD 四同步（代码/文档/台账/交付物）照旧。
6. **v1.2 拍板结论（2026-11-10，全部采纳本文建议）**：**甲路线**（组织级隔离，不启用 RLS）｜ **orgs 独立表**｜ **企业/创业者自助激活，交付者与区域审核**｜ **先免费额度、订阅随 M6 落结构**｜ **现服务器不扩容先试点**｜ **W0 与商用平台分离**｜ **试用客户 M1 后再评估迁移**｜ **`org_id=NULL` = 平台身份不受 org 限制**（存量回归面最小）｜ **交付者供给由 `OWNER` 亲自兼任首交付者**。**MVP 范围 = M1 + M2 + M3a/c/b + M5 四 Goal 先行**（MT-B 即第一个对外里程碑），M6 计费结构与 M7 区域商机按真实反馈后置。

## 4. 架构决策：分级隔离路线（本文核心，`OWNER` 拍板点 §11-1）

### 4.1 甲路线（本文基线）：组织级隔离，复用既有成员模型

```
orgs（新表，主体承载）
  ├─ users.org_id（企业成员归属；创业者/交付者/区域服务商 org_id = NULL + 各自身份表）
  ├─ projects.org_id（项目归属企业；迁移回填：存量项目 → 内部 org）
  └─ project_members（既有，零改动——成员可见性即隔离边界）
```

- **项目域 67 张表**：经 `projects.org_id` 推导，不逐表加列；访问统一走 `project_access`（现 `projects/permissions.py:23-55` 的 Python 过滤**改造为带 org 维度的统一入口**，见 M3）。
- **全局 63 张表**：M0 逐表判定为三类——`平台共享只读`（模板/模块目录/技能目录，企业只读）、`平台私有`（系统配置/结算配置，企业不可见）、`须主体隔离`（AI 配置偏好、模拟 run、通知等→ M4 逐个处理）。
- **122 个全局写端点**：逐端点判定「平台管理员专属 / 主体自助 / 需 org 维度」，M3 改造。
- **Redis 12 键族**：登录限流已含用户维度（`auth:login_fail:<user>:*`）；预算键、执行键、API-action 键加主体维度（M4）。
- **存储 2 根**：`storage/local.py` 路径加 `{org_id}/` 段（M4）。
- **JWT**：现 7 claim 加 `org_id`（可空=平台身份）；`auth/decorators.py` 378 处经统一装饰器扩展吸收，不逐处手改。
- **RLS**：甲路线**不启用** PG RLS——隔离靠应用层统一入口；乙路线再启用（M0 评估连接池与 RLS 的兼容成本）。

**甲的风险与对策**（评估文档 §5 同源）：
- 漏判一个全局写端点 = 跨企业泄露 ⇒ M3 逐端点判定表 + 跨企业越权测试专项（§9）；高风险面（调研表/文件/对话/导出）加自动化越权用例。
- 应用层过滤漏一处即泄 ⇒ M8 用「企业 A 账号全 API 爬扫企业 B 资源」的红队式回归兜底。

### 4.2 乙路线（规模化演进保留）：全量 tenant_id + RLS

触发条件（满足其一即启动乙升级设计）：付费企业 > 20 家；出现合规级隔离要求（客户合同要求数据物理/行级隔离）；单实例查询性能因跨 org 扫描劣化。届时按评估文档 §2.B 的 660+ 点位清单执行，甲路线的 orgs/归属数据是乙的直接前置（不白做）。

### 4.3 容量与性能口径（M0 须实测补齐）

评估文档未测**并发性能**（它测的是工程量）。M0 补三项实测：① 单实例在 10/50/100 并发登录下的 API P95；② worker 单队列在多企业任务并发下的吞吐；③ PG 连接池上限与 4 个 gunicorn worker 的配置余量。**在实测前，本文不承诺任何并发数字**；对外宣传口径一律写「支持多企业同时在线」，不写具体并发数。

## 7. Goal 详单（目标 / 语义 / 验收）

### M0 决策与盘点轮（零业务代码）

- **目标**：把本文所有「待拍板/待实测」收敛为可执行口径。
- **语义**：产出 4 份 ADR——ADR-M1 租户模型（甲/乙，§11-1 的评审材料）、ADR-M2 主体-角色映射（与 ADR-001/002/006 对齐，明确四类主体 × `users.role` × 商业字段的三层关系）、ADR-M3 全局面判定规则（63 表逐表 → 三类处置）、ADR-M4 注册审核策略（§11-3）；产出《全局面盘点表》（63 表 × 122 写端点 × 12 Redis 键族 × 2 存储根，逐项标注处置）；产出容量实测报告（§4.3 三项）；按口径纪律重测 130/63/122/391/49/241/378 等基线数字（不同快照口径并存，以重测为准）。
- **验收**：4 ADR + 盘点表 + 实测报告入库 `docs/commercialization/multi-tenant/`；`OWNER` 对 §11 五个拍板点逐项签署；无代码/迁移/路由改动。

### M1 主体与组织底座

- **目标**：org 实体、归属关系、迁移回填、审计维度落地。
- **语义**：`orgs` 表（含类型：enterprise/internal，internal=平台自有）；`users.org_id`（可空）；`projects.org_id`（回填到 internal org）；`operation_events.org_id`（可空=平台级）；种子与 `cli.py` 补 org；**企业成员复用 `add_project_member`，零新建平行权限表**（G6 红线）。
- **验收**：迁移链干净（up/down 对称）；存量数据回填后 2 个演示项目归 internal org；「企业 A 建项目 → 企业 B 不可见」在集成测试成立；全量回归绿。

### M2 四类自助注册与认证

- **目标**：四入口注册、验证、状态机、登录打通。
- **语义**：`POST /api/v1/auth/register/{enterprise|founder|deliverer|partner}`（入口隔离，GAP-13/三入口语义对齐 G2）；邮箱验证（SES 复用，验证链接一次性）；注册状态机 `pending_email → pending_review（可选）/ active / suspended`；初始角色按 §3 矩阵；交付者注册可要求补充 R 分层申请材料（G1 证据链）；区域服务商注册落「待合规审查」态（GAP-12 售卖开关默认关）。登录限流复用既有 `auth:login_fail` 键族；**注册面反滥用三件：邀请/验证令牌一次性、同 IP 注册限流、区域服务商入口默认置后**（v1.1 补，sec 评审）。
- **验收**：四类账号可自助注册并登录；审核制开关生效（§11-3 拍板值）；越权注册场景（重复邮箱、已存在主体、未验证邮箱登录）全部 4xx 且留痕。

### M3 统一隔离入口与全局写端点改造（v1.1 拆分为三步，eng 评审）

- **目标**：把「企业只见本企业」从约定变成架构保证。
- **M3a 统一入口（1–2 天）**：`projects/permissions.py` 改造为带 org 维度的统一访问入口（查询下推到 SQL，替换 Python 全表扫描——现 `visible_project_ids` 被 agents/handover/meetings/transcripts/projects 五域消费，arch 评审确认消费方即盘点维度）；JWT 加 `org_id` claim（可空=平台身份）；**先写装饰器扩展行为规格再动手**（378 处批量改是 Agent 盲改高危区，规格先行才可批量）。
- **M3c 越权套件前置（TDD 顺序）**：跨企业越权测试骨架**先于端点改造合入**——套件先红，M3b 端点批批改造批批转绿。套件覆盖：项目/调研表/文件/导出/AI 执行状态/API-action 确认/对话，企业 A token 打企业 B 资源全 403/404。
- **M3b 端点分批销号（3–4 批，每批 ≤30 个）**：按 M0 盘点表逐批改造 122 个全局写端点（判定：`admin-only 保持 / 加 org 校验 / 开放为自助`），**每批独立 PR 且与该批越权用例同 PR**（提示词第 14 条）；批间可并行但同域端点不得跨批。
- **验收**：盘点表 100% 销号（每端点一行「处置 + 测试指针」）；越权套件进 CI 且全绿；热点文件预算闸不破（隔离逻辑不写进 `projects/service.py`——eng 评审）；全量回归绿。

### M4 全局面治理（Redis / 存储 / 队列 / AI 预算）

- **目标**：非 DB 面的主体隔离与计量。
- **语义**：Redis 预算键、AI 执行键、API-action 键加主体维度；`fde:ai-execution:{id}` **必须加 actor 归属校验**（v1.1 升级为必做——sec 评审裁定 UUID 不可枚举不足以作为防线）；存储根加 `{org_id}/` 段，**存量文件迁移方案：双写期（新旧路径同写）→ 校验和逐文件核对 → 切读 → 旧路径只读 → 删除**（v1.1 补，sec 评审——迁移期隔离不降级）；队列 job 携带主体标签用于计量；**AI 预算闸从整实例单值改为按主体额度**（GAP-04 额度账承接，平台汇总额度仍在模型服务商控制台兜底——评估文档 §7 三纪律保留）；**供应商只允许按量付费 key**（评估文档 §7.0 合规结论，商用后自动升级为红线）。
- **验收**：主体 A 的 AI 用量只计 A 的额度账；A 无法读取 B 的 execution 状态/事件流；存储路径越权访问测试通过；预算超额在**主体级**触发 `budget_blocked` 并留痕。

### M5 企业空间与自助交付（对齐 G6，消费 G2 产物）

- **目标**：S1 场景端到端。
- **语义**：企业空间视图（我的项目/成员/邀请/额度/诊断/分流记录）；邀请成员（邮件 + `add_project_member`；**邀请链接一次性令牌 + 邀请人可见被邀者身份 + 成员变动通知全组织**——v1.1 补，sec 评审认定邀请是社工攻击面）；三档分流判定留痕（GAP-14：定性判据 + 交付咨询人工判定，无量化阈值硬编码）；六项交付物完成判据聚合与三档呈现（GAP-05，复用既有产物）；诊断完成后系统呈现三付费选项 + 平台顾问跟进（G6 口径：企业自主选择不被取消）。
- **验收**：一家测试企业从注册到拿到三付费选项全程无人工建号；分流可回看；G6 任务书验收清单逐项过。

### M6 配额、席位与科目层（对齐 G2/G3）

- **目标**：商业计量结构落地（金额不预写，配置位缺省不可收款——G 线纪律）。
- **语义**：额度账（按主体、一次一主体、不重置）；席位订阅与激活流（挂结项验收后扣费，方案 A 一次性扣除——GAP-07 已选定的书面承载）；收入科目层（GAP-09，份额算法复用 `seat_shares_for`）；认证费独立收费项 + 模拟考核驱动状态（GAP-08）。
- **验收**：G3 任务书验收清单逐项过；所有计费名目有归属、无硬编码数值；席位激活反例用例（未验收不扣费）通过。

### M7 商机归属与区域服务商（对齐 G4/G5）

- **目标**：S5 场景端到端（渠道侧能力，售卖默认关）。
- **语义**：七步归属链（报备→企业确认→平台确认→保护期→售前→撮合→结算；规则数值可配置**不预写默认值**；已确认归属不因企业自行注册转移——GAP-11 反例用例）；**商机数据归属权写死：平台托管、企业确认前区域服务商不可导出客户名单、双方按授权可见**（v1.1 补，sec 评审——渠道客户名单是商业敏感资产，归属不写死会成为渠道纠纷源头）；区域四阶段落库 + 售卖开关默认关 + 合规条件清单登记（ADR-005 于本 Goal 成文，「两店一年」条款登记）。
- **验收**：G4/G5 任务书验收清单逐项过；售卖开关关闭态下区域伙伴无法进入售卖流。

### M8 全量回归、安全专项与真实试点

- **目标**：商用态放行。
- **语义**：9 类测试（G 线 §12 清单）+ 新增跨企业越权/重放/敏感日志专项；存量全量回归（pytest/vitest 以当时 CI 实测为准）；**2–3 家真实试点企业**（从试用客户转化）走完 S1 全程；试点反馈回写 M5；试用轮 W0 与新平台并存期的主备/数据隔离方案另附。
- **验收**：安全专项零高危；试点企业完成率与 NPS 口径由 `OWNER` 定；**放行签核**：本文 §12 三闸对齐现行闸模式（开发闸/暴露闸/上线闸），签核人 `OWNER`。
