## 五份报告的关键修订条件（已全部落回 v1.1）

### eng-reviewer-3（4 条件）
1. **M3 拆分**：M3a（permissions.py SQL 下推 + JWT org claim，1-2 天）→ **M3c 前置**（越权套件骨架先合入，TDD 顺序——套件先红，端点改造批批转绿）→ M3b（122 端点按域分批销号，每批 ≤30 个、独立 PR、批批附越权用例，3-4 批）。
2. **`org_id=NULL` 语义进 ADR-M2 显式拍板**：定为「平台身份不受 org 限制」——该单点决策决定存量回归面是 30 个文件还是 300 个文件（实测 102 个测试文件直接构造 `User(...)`）。
3. **§13 提示词 10→14 条**：补「全量回归附 CI run 链接」「隔离轮禁顺手改业务逻辑」「热点文件预算闸（service.py ≤1946 只许变小 / mypy 279 只许减）」「并行 Goal 同文件冲突纪律」「M3b 每批端点与越权用例同 PR」。
4. **排期改日历口径**：36-58 工程日 × 1.5-2× ≈ **55-115 日历工作日（约 3-5.5 个月）**；对 Agent 写码速度可乐观（0.7×），对拍板/验收/CI 等待人肉环节须悲观（2-3×）。

### sec-reviewer（6 项）
1. AI execution 键按 execution_id 直取——UUID 不可枚举**不足以**作为防线，须加 actor 归属校验（M4 落位）。
2. 存储 `{org_id}/` 迁移期双写/校验和方案缺失——补进 M4 语义。
3. **R4 改写**：原表述与 AGENTS.md「客户真实资料永不进数据库」矛盾。改写为：企业空间存的是**企业自己授权存于平台的业务资料**（产品承诺），但平台侧代码/文档/日志仍执行代号化；客户资料所有权归企业，平台不得用于其他用途。
4. **邀请社工面**（任务书未提）：企业成员邀请是新的社工攻击面——邀请链接一次性 + 邀请人可见被邀者 + 成员变动通知全组织，落 M5。
5. 商机数据归属权：区域服务商报备的商机（客户名单）归属权与导出权须在 M7 写死（平台托管、双方按授权可见、企业确认前区域不可导出名单）。
6. 注册反滥用补三件：邀请一次性令牌、同 IP 注册限流、区域入口默认置后。

### biz-reviewer-3（3 硬伤）
1. 交付者初始权限 `fde_engineer` 与 G 线「派单前须进供给池审核」冲突——改为注册后默认 viewer + 供给池申请流（GAP-01 证据链）。
2. M5-M7 消费 G2-G5 产物但 G 线无排期承诺——M0 须产出 G/M 线联合排期，否则 M5 排期是空中楼阁。
3. 商业盲点：任务书通篇工程不谈市场——补 §17「市场与供给假设」（交付者冷启动、试用客户转化路径、竞争定位），标注为 `OWNER` 经营决策项，不代答。

### arch-reviewer（关键项）
1. 甲路线「67 表推导」验证：`visible_project_ids` 被 5 个域消费（agents/handover/meetings/transcripts/projects）——漏网面存在的证明，M0 盘点表须把「消费方」也列为盘点维度。
2. 378 装饰器统一扩展可行，但须先写「装饰器扩展的行为规格」再动手（否则 378 处批量改是 Agent 盲改高危区）。
3. Redis 键族分级：安全攸关（登录限流/API-action）与计量类分开处理；API-action 确认键跨主体风险最高。

### product-reviewer-2（关键项）
1. **MVP 聚焦**：最小组商用量 = M1+M2+M3+M5（四 Goal），M6/M7 可延后——先让 2 家企业安全并发，计费与渠道后置。

3. **试用客户过渡两难**：§11-6 只说资源分离没说客户过渡——补「试用客户迁移三选一」拍板点（不迁/手动迁/M1 后迁），须 `OWNER` 拍板。
4. 竞争定位缺失——并入 §17 经营假设项。
