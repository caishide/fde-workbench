## §0 结论速览

1. **融合形态＝统一内核＋双门面＋认领续翻**（承领导拍板，本稿细化到可拆轮实施粒度）：内核＝「问题条目契约公共子集 ＋ 评分方法论」两件抽象，不是搬家式合并；双门面信任模型差异是红线级（公网匿名 vs 内网 JWT），永不合一。
2. **内核落点推荐 guidance 域旁扩层**（§5 方案 E1）：两模块**今天就已经各自依赖 guidance 域**（translator 4 处 import：`translator/jobs.py:22-25`、`translator/service.py:23-25`；diagnostics 3 处：`diagnostics/service.py:42-43`、`diagnostics/jobs.py:40-41`——锚点 A21/A22）——内核落 guidance 域＝**零新增跨域依赖方向**，落新顶层包＝两模块各加一条新依赖边且制造第四个理解域。
3. **认领续翻＝T-11 之后的显式动作**：诊断会话认领（获客诊断任务书 W2 独立轮，现未实施——`diagnostics/routes.py` 无 claim 路由，锚点 A17）→ 认领人在内网 translator 门户发起「自诊断会话续翻」，经**字符串软链**（`source_ref`，无外键）进 translator 域；诊断表零外键指向 projects 的死规矩不变、公网路由集合（9 条）不变、AI 不自动发起。
4. **评分方法论整建制可移植**：`simulation/diagnostic_judge.py` 本就是「文本 vs 参考材料」通用评分器＋元验证闸（锚点 A19）；移植形态＝per-purpose 注册表（rubric/锚点/反例/噪声带按用途隔离），**只在离线评测侧运行**（scripts/diagnostic_eval/ 域），在线链路仍只保留机械契约闸；答案材料与夹具永不进 server/src（污染隔离纪律照旧）。

6. **待领导拍板的 4 项**（本稿不预设结论，全部给了推荐）：拍板 ①内核落点（推荐 E1 guidance 域旁）；②AI 调用入口是否在后续轮统一（推荐：暂不统一，双通道各守各的纪律，统一另行立项）；③评分确认走离线评测形态（推荐：是，在线 judge 否决）；④F3 续翻轮依赖 T-11 的排期确认（推荐：T-11 完成后启动，本稿 §6 已按此标注）。

## §2 统一内核边界

### §2.1 共享什么（内核两件抽象）

**内核件一：问题条目契约公共子集。** 两模块的输出本质是同一种东西——「客户诉求→结构化问题清单」，只是下游形态不同（translator 出 guidance 条目集，diagnostics 出诊断报告卡的问题层）。公共子集＝条目级五元：

| 公共子集元 | translator/guidance 侧现状 | diagnostics 侧现状 |
| --- | --- | --- |
| 条目文本 | `text`（≤2000 字校验，ai_schema.py:69） | `findings[].problem`（R-5 一一映射的问题标题） |
| 分类/严重度轴 | `classification` 闭集 ＋ `severity`(high/medium/low) ＋ `module`（交付模块名，仅问题清单字段） | 问题↔动作一一映射（R-5：每个 finding id 必须有对应 action） |
| 溯源义务 | `source_refs` 必须引用原文位置（ai_schema.py:75-78 unknown_source_ref／missing_source_ref——事实与 AI 判断必须引用原文） | 数字闸可溯源集合＝问卷答案＋政策引文（R-4；number-gate-v2 口径） |
| 人工确认态 | `confirmed` bool（AI 恒 false——提示词钉 A25＋校验器钉 A24 双重钉） | 草稿态不可被下游消费（报告只在留资后可见；认领是显式转化动作 A16） |

抽层方向（实施轮细化）：把「条目形状校验＋溯源义务校验＋AI 只出草稿语义」收敛为**单一权威点**（落点见 §5 拍板项①），双门面各自在其上映射自己的下游形态；任何一侧不得私藏第二份契约常量。

**内核件二：评分方法论。** diagnostics 已实证的评分三件套整建制可移植（详见 §4）：①judge＝「文本 vs 参考材料」通用评分器，不知答案字段形状（`diagnostic_judge.py`，分层纪律：答案装配只在评测脚本侧）；②元验证闸先于逐卡评分（锚点落带＋反例拒评；缺失 ⇒ insufficient_data 不默认通过，A19）；③分布读数（同配置多 run 分组、噪声带、n≥3 可判定规则）——单点分差永不作能力变化判定。

**方法共识（不抽代码，写入内核原则）：确定性优先、AI 只做语言转换。** translator 的脱敏管线（词典替换 fail-closed）、diagnostics 的测算卡（`compute_assessment` 纯规则确定性，`diagnostics/assessment.py:125-126`——同答案必同结果）同体现此原则：凡可确定的绝不交给模型，模型输出永远过机械契约闸。

- 结构已预留认领形态：status 五态含 `claimed`（A15）、`claimed_by_user_id` 指针列（A16）、90 天认领窗口（A16）、**认领＝显式转化动作且须平台接受（claimed ≠ accepted）**（A16）。
- `lead_diagnostic_sessions` 零外键指向 projects 的死规矩（A16）——**本链路全程不破坏**。

### §3.2 链路设计（推荐方案 A′）

```
[公网] 匿名自诊会话 → submitted → report_ready
   │  （T-11 轮：认领闸——认领人认领 → 平台接受）
   ▼
[内网] 认领人（FDE 席位，JWT）在 translator 门户发起「自诊断会话续翻」
   │  POST /api/v1/translator/translations（既有路由，不新增公网路由）
   │  请求带可选 source_ref = "lead_diagnostic_session:<session_id>"（字符串软链）
   │  预填来源 = 诊断会话已落库的脱敏结构化字段（经 diagnostics 域只读函数）
   ▼
translator_translations 新行（created_by=认领人；source_ref 软链落列）
   │  既有管线不变：DeepSeekClient 草稿 → validate_guidance_output → redact_draft_payload
   ▼
[内网] 采纳 adopt（既有路由 A5）→ 进项目 guidance 指引（此时才触及 projects 域）
```

要点：

1. **续翻动作只存在于内网 JWT 面**：diagnostics 公网路由集合恒 9 条不变；续翻入口＝既有 `POST /translations`（A3）扩可选 `source_ref` 字段，公网面零感知。
2. **软链不落外键**：`translator_translations.source_ref` 为可空字符串指针（形如 `lead_diagnostic_session:<id>`），可选 `source_sha256` 指纹列佐证可溯；两表之间、以及任何到 projects 的外键，零新增。
3. **预填的落库边界（T-A2 张力显式处理）**：续翻预填只读**诊断会话已在诊断库落存的脱敏结构化字段**（该落库发生在 diagnostics 域自己的纪律内）；translator 行照旧**不落输入原文**（只落输出草稿）——续翻不新增任何落库面。
4. **权限随认领链**：仅 T-11 认领并接受的认领人（或平台身份，走跨 org 留痕既有纪律）可对该会话发起续翻；服务层校验，不做路由级白名单。
5. **AI 不自动发起**：续翻是人的显式动作；无事件订阅、无后台自动创建翻译任务的通道。

### §3.3 不变的死规矩（机械闸承载，见 §6 轮 F3）

1. `lead_diagnostic_sessions` 零外键指向 projects（A16 metadata 扫描钉同款手法扩展到 `translator_translations.source_ref` 无 FK 断言）。
2. diagnostics 蓝图路由集合恒 9 条（蓝图注册表同步闸家族）。
3. translator 域对诊断数据**只读**：经 diagnostics 域提供的只读函数取预填，禁直接 ORM 写诊断表；跨模块 import 用函数内懒导入（包环冻结闸纪律）。
4. 不加公网路由；不自动发起。

### §3.4 链路内多方案对照

| 方案 | 内容 | 裁决 |
| --- | --- | --- |
| **A′ 软链字段（推荐）** | translator 行加 `source_ref` 字符串软链＋可选 sha256；续翻经既有内网路由 | **推荐**：零外键、零公网面、可溯、改动面最小 |
| B 反向外键 | 诊断表加指向 translator/项目的外键 | **否决**：直接违反「诊断表零外键指向 projects」死规矩（红线级）；把线索域耦合进内部交付域 |
| C 事件驱动自动续翻 | 认领事件触发后台自动创建翻译任务 | **否决**：AI/系统代发起＝自动化越权（人工显式动作是红线）；且为公网面数据自动流入内部域开了无人把关的通道 |
| D 诊断域内直接出 guidance | 在 diagnostics 域内复刻 translator 管线 | **否决**：两份翻译管线必然漂移；公网面引入内部交付契约＝信任模型污染 |

## §4 评分移植方案

### §4.1 现状方法论盘点（全部已实证）

- **judge**：`simulation/diagnostic_judge.py`——通用「文本 vs 参考材料」评分器；rubric v0.2（A19）；total/verdict 服务端重算。
- **元验证闸**（B#23 先例「评测器本身先过闸」）：锚点须落期望带＋反例须被拒评才 pass；锚点缺失 ⇒ `insufficient_data` 不默认通过（A19）。
- **分布读数**：逐卡四轴分组（eval_set_version×prompt_version×number_gate_version×judge_version）、锚点两轴可合并、n≥3 才可判定、严格大于噪声带（纯 judge 噪声带实测 9 分）——单点分差不可作能力变化判定。

### §4.2 泛化设计：per-purpose 注册表

1. judge 模块**位置不动**（server/src 的 simulation 域——它本身不知答案字段形状，不是答案材料），**注册表化**：`purpose → {rubric 版本, 锚点夹具集指针, 反例集指针, 阈值/噪声带口径, judge_version}`；translator 侧新增 purpose（如 `translator_guidance_v1`）只是在注册表加行。
2. **夹具放评测脚本侧**（scripts/diagnostic_eval/ 域或其旁）：锚点＝真相层留存的优秀样例（仓库只存指针+sha256），反例＝编造/越权坏样例；**答案材料与夹具原件永不进 server/src**——污染隔离七钉照旧全绿，评测 purpose 扩展不豁免。
3. **judge 只读参考材料**：judge 输入＝被评产物＋参考材料，不知答案字段形状（T-07/T-08 既有分层纪律原样复用：装配只在脚本侧）。
4. **分布读数原语复用**：purpose 加入分组轴；元验证闸先于逐卡评分不变；translator purpose 首批曲线点按同一可判定规则读数（n≥3 前一律 insufficient_data，不编造结论）。

### §4.3 translator purpose 的评分语义（草案，实施轮细化）

| 维度 | 评什么 | 对应 translator 既有闸 |
| --- | --- | --- |
| 忠实度 | 草稿是否忠于输入三段（不得引入输入中没有的事实） | 对应 guidance 契约 source_refs 溯源义务（A24） |
| 结构合规 | 条目五元齐整、分类闭集、问题清单可用性 | `validate_guidance_output` 机械闸（在线已有）——评分层评「机器闸之上的质量」 |
| 无编造 | 分类、严重度、模块名是否有输入依据 | severity/module 扩展字段无在线闸 ⇒ 评分层是唯一质检面（移植的主要收益点） |
| 越权否决 | 草稿不得含确认/拍板语义（confirmed 恒 false 的实质面） | 提示词钉（A25） |

### §4.4 双 AI 通道差异的处置（偏差②）

- **现状如实**：diagnostics 走 `execute_ai_prompt` 单一入口（预算闸＋N2 归因在入口内，A20）；translator 走 `DeepSeekClient` 直连（goal-d14 拍板「与 AI 聊天同源解析模型」，A8）， translator 行自身已落 `ai_model`/`ai_generated_at` 归因列。
- **本稿处置（默认，不动现状）**：评分/评测是**离线评测进程**的行为——生成走两模块各自既有生产通道，judge 客户端只在评测进程内实例化（现状如此）；**生产在线链路零新增 AI 调用点**，J 系列提示词闸与入口白名单闸（A28）照旧约束。
- **拍板项②（不预设）**：是否在后续轮把 translator 迁往 `execute_ai_prompt` 统一入口——收益＝归因/预算闸单点化；代价＝goal-d14「聊天同源」语义重裁定＋模型偏好链迁移。**推荐：暂不统一**（两通道各守各的纪律且都有归因），统一另行立项。

### §4.5 否决项

| 方案 | 否决理由 |
| --- | --- |
| 在线 judge（每次翻译/报告生成后实时评分） | ①token 成本翻倍且公网面延迟不可接受；②judge 噪声带 9 分使单点分数不可判定——在线评分给出的数字是伪精度；③评分的价值在迭代提示词与生成器（离线曲线），不在拦截（拦截已有机械契约闸） |
| judge 进生产在线链路做软闸 | 同上，且「评分不过则拒绝草稿」会把 judge 噪声变成用户可见的随机失败 |
| 评分夹具进 server/src（图省事） | 违反评测集污染隔离纪律（答案材料不进 server/src 的机械七钉）；夹具只存指针+sha256 于仓库、原件留真相层 |
