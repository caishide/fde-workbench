## 4. r1 遗留问题专项裁决：C 口径「执行落空」假阳性与 B 口径 `executed` 分母归属

### 4.1 源码级根因（为什么 2 行 `approved` 永远不会有 `executed_at`）

核对 `server/src/fde_api/control/models.py`、`control/service.py`、`workflows/settlement.py` 与 `agents/receipt.py`，`automation_approvals` 表在当前架构下由**三条异构轨道共用**，但生命周期终态不同：

1. **A 轨 · DSH 审批后执行**（`control/service.py:617-652` 创建，`run_id IS NOT NULL, workflow_node_run_id IS NULL`）：
   - 人工调 `decide_automation_approval`（`:776`）先把 `status` 置为 `'approved'`；
   - 随后必须调 `execute_approved_dsh_tool`（`:828-893`，硬白名单唯一允许 `capability == "task.batch_assign"` 且 `tool_name == "project_tasks.batch_assign"`，见 `:873`），执行成功后才置 `approval.status = "executed"` 与 `approval.executed_at = datetime.now(UTC)`（`:888-889`）。
   - **只有这一条轨道存在「批准 → 执行」两阶段间隙，因此只有这一条轨道可能发生真正的「执行落空」！**
2. **C 轨 · 工作流 `human_approval` 人工门**（`control/service.py:657-671` 创建，`run_id IS NULL, workflow_node_run_id IS NOT NULL, tool_name = "workflow.human_approval"`）：
   - `decide_automation_approval` 在同一数据库事务内直接调用 `workflows/settlement.py:235-295` `settle_approval_node`，把 `WorkflowNodeRun.status` 置为 `'succeeded'` 并投递下游 `workflow.run`；
   - `approval.status` 的设计终态就是 `'approved'`，`executed_at` 恒为 `NULL`；
   - 若有人对其调用 `execute_approved_dsh_tool`，`control/service.py:850-854` 显式拦截并抛 **409 `approval_not_executable`**（原文：`「工作流审批在拍板时即生效，无需执行步骤。」`）。
3. **D 轨 · Agent 回执升级人工门**（`agents/receipt.py:175-254` `request_ask`，`run_id IS NULL, workflow_node_run_id IS NULL, tool_name = "agent.receipt.ask", risk_level = 4`）：
   - 同样是纯人工裁决门，无 `execute_approved_dsh_tool` 执行后腿，`executed_at` 恒为 `NULL`。

### 4.2 口径裁决结论（r1 移交项正式结案）

- **C 口径（执行落空）裁决**：原 SQL `WHERE status = 'approved' AND executed_at IS NULL AND reviewed_at < now() - interval '1 hour'` 漏加**轨道限定谓词**，把 C/D 轨「拍板即终态」的正常完结行全数误判为「执行落空」。**准确谓词应限定在存在执行后腿的 A 轨行**：
  ```sql
  WHERE status = 'approved'
    AND run_id IS NOT NULL
    AND workflow_node_run_id IS NULL
    AND executed_at IS NULL
    AND reviewed_at < now() - interval '1 hour'
  ```
  按修正谓词在活库实跑，结果 = **`0 rows`（真实执行落空率 = 0）**。r1 登记的 `df31cb16…` 与 `b789a318…` 正式销号为**口径假阳性**。
- **B 口径（`executed` 状态与分母关系）裁决**：`AUTOMATION_APPROVAL_STATUSES` 五态中，`executed` 是 A 轨审批在 `approved` 之后走完 `execute_approved_dsh_tool` 的成功终态（非独立于 `approved` 的第三种审阅意见）。因此计算人工否决率时：
  - **规范公式应为 `rejected / NULLIF(approved + executed + rejected, 0)`**（`pending` 未决、`expired` 超时未审仍单列不入分母）；若把 `executed` 排除在分母外，一旦 A 轨真实跑通，所有成功执行的正样本都会从分母消失，导致否决率被系统性高估甚至变成 `0/0`。
  - 在当前活库时点（`executed = 0`），旧公式 `rejected / (approved + rejected)` 与修正公式数值恒同（均为 `0 / 2 = 0.0000`），历史可比性零断裂；后续更新本地 `verify-run-evidence.sql` 时并列输出两列即可平滑过渡。
