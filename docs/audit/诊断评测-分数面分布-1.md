## 一、为什么必须做分布面（登记事实）

curve 3 已登记一条硬事实：**锚点 A2 在同一份输入（meta-v0.2 夹具，逐字节固定）上，两次评分 77 → 84** ⇒ judge 单点分数噪声 **≥7 分**；逐卡 ±10 以内属噪声域。

**推论（此前一直靠自觉守，现在机械执行）**：同考卷两次 run 的逐卡分差**不得**直接解读为生成器能力变化。要读分数面，必须先有**分布**——同考卷多 run 重复取样，把「噪声宽度」显式测出来，再按噪声带判定差值。

本轮交付三件东西：**分布原语**（`scripts/diagnostic_eval/eval_lib.py`）、**判定规则**（`delta-noise-band-2026-11-11`）、**底册 CLI**（`scripts/diagnostic_eval/summarize_distributions.py`）。本文件是它的**第一次真机读数**。

## 二、读数规则 `delta-noise-band-2026-11-11`

### 2.1 判定式

> **分数差 Δ 可判定 ⇔ 参与比较的两组样本数各 ≥ `MIN_DISTRIBUTION_RUNS`(=3) ∧ |Δ| > 噪声带**
> 噪声带＝参与比较的各分布的**观测极差较大者**（含锚点纯 judge 噪声极差）。

三条读法约定：

1. **严格大于**：`|Δ|` 恰等于噪声带 ⇒ 落在噪声域内，**不可判定**（不写「刚好持平」这种含糊话）。
2. **n 不足 ⇒ `insufficient_data`**，语义是「**还没资格判**」，不是「不可判定」——两者必须分清：前者是数据不够，后者是差值落在噪声里。
3. **规则本身不产结论**：它只回答「这个差值能不能读」，不回答「生成器变好没有」。后者还需要逐卡分布 + 阈值校准（E-1 未完成）。

### 2.2 两类可比组（**轴不同，不可混用**）

| 组 | 分组轴 | 为什么 |
|---|---|---|
| **逐卡组** | 四轴：`eval_set_version` × `prompt_version` × `number_gate_version` × `judge_version` | 只有四轴全同，重跑得分才是**同位样本**；任一轴不同就不是同一分布（改考卷＝C 类改考题，改生成器＝换了被测物） |
| **锚点组** | 两轴：`judge_version` × `meta_fixture_version` | 锚点输入**逐字节固定**（真相层夹具）⇒ 锚点重跑得分＝**纯 judge 噪声**，与生成器版本无关 ⇒ 锚点分**可跨生成器版本合并** |

> **锚点可合并、逐卡不可合并**——这是本规则最容易做错的一处：curve 2 的 A2=77 与 curve 3 的 A2=84 来自**不同的生成器 run**，但它们是**同位 judge 噪声样本**（同一 judge 规则、同一夹具、同一份输入）⇒ 合并进同一个锚点分布；逐卡则必须四轴全同才可合并。

### 2.3 三条机械不变量（代码执行，不靠文档自觉）

1. **元验证不过的 run 整个不收**：只有 `usable_as_evolution_evidence=True` 的 run 进入分布（协议语义在代码里执行）。
2. **judge error 行与复述作废行**——**不是 0 分，是无数据**：从分布中**排除**，并如实上报 `excluded_rows` 计数。假 0 分会直接污染噪声带宽度。
3. **不编造统计量**：n<2 ⇒ `stdev=None`（不写 0）；空样本 ⇒ 直接失败，不产空分布。

### 2.4 边界（不得越界）

- **噪声带＝观测极差**，不是统计置信区间。n=3 的极差**偏窄**（只取到 3 个样本的 min/max）⇒ 本规则**偏保守**（更倾向判不可判定），不会给出虚假的「变好」。
- **逐卡极差＝生成器 + judge 联合噪声**；**锚点极差＝纯 judge 噪声**（更窄）⇒ 判定取参与分布的**较大者**（保守侧）。
- **本规则不产生任何通过线**：oracle 数据未攒够（E-1），任何「≥80 分即达标」的写法仍是越界。
- **规则的适用对象是「两组均值的差」**，不是「两组离散度的差」——后者（谁更稳）不在本规则判定式内，见 §4.3 的口径声明。

### 4.1 判定一：版本差（v1 组 vs v2 组，同卡）——**不可判定**

| 卡 | v1 均值(n) | v2 均值(n) | Δ | 规则输出 |
|---|---|---|---|---|
| datawhale-009 | 77.0 (n=1) | 70.7 (n=3) | −6.3 | `decidable=None, reason=insufficient_data`（n_list=[1,3]） |
| datawhale-023 | 86.0 (n=1) | 79.0 (n=3) | −7.0 | `decidable=None, reason=insufficient_data`（n_list=[1,3]） |
| somwyn | 60.0 (n=1) | 55.0 (n=3) | −5.0 | `decidable=None, reason=insufficient_data`（n_list=[1,3]） |

**读法**：`prompt-v1` 组只有 **1 个 run** ⇒ 规则机械地拒绝出结论——**「还没资格判」**，不是「判出没差别」。三个 Δ 恰好都落在 ±7 附近、且 v1 均值都比 v2 高，看着像「生成器变差了」，但**规则不许这么读**：v1 侧没有分布，单点差与 judge 噪声无法区分。
**消解条件**：v1 组补到 n≥3（同一考卷 `2026-11-11`、prompt-v1、rubric-v0.2 再跑两轮）⇒ 版本差即可判。

**读法（不得越界）**：
- **可判定的只有两句**：① `datawhale-010` 与 `somwyn` 的分数分布**可判定地低于** A2 参考锚点（Δ 分别为 −14.0 与 −27.0，均超出 9 分的纯 judge 噪声带）；② 除 `datawhale-001` 外，五张卡的分布**可判定地低于** A1 顶格锚点。
- **`datawhale-001` 对 A1 是 `within_noise`**：它的 Δ(−17.1) 没有超过它**自己**的观测极差(18.0)——噪声带取参与分布的较大者，保守侧生效。这条恰恰说明规则的保守性：**不会因为「差得挺多」就放行**。
- **`datawhale-009` 对 A2 是 `within_noise`**：Δ(−11.3) 小于它自身极差(21.0)。它对 A1 反而可判定（Δ −29.1 > 21.0）。
- **「可判定地低于锚点」≠「不达标」**：通过线未校准（E-1），本文件不给任何达标/不达标结论，只给「差值是否超出噪声带」。

### 4.3 关于「离散度」的读法声明（本轮新增口径，登记可推翻）

**规则判定式只管「两组均值的差」**，不管「两组离散度谁更大」。所以下面这句是**算术读数**，不是规则判定：

> 同配置（prompt-v2＋number-gate-v2）三次 run 的逐卡观测极差为 **5–21 分**（009 卡最大 21 分），而纯 judge 噪声的观测极差是 **1–9 分**（A2 = 9）。**超出 9 分的那部分不可能来自 judge 抖动**（judge 噪声上界已由锚点四样本测得），只能来自**生成端方差**。

这条是本轮最有价值的事实：**逐卡分差之所以读不出能力变化，主因不是 judge 抖，而是生成端本身就抖**（009 卡同一份考卷同一套提示词，三次 run 差 21 分）。但「离散度归因」**不在** `delta-noise-band-2026-11-11` 的判定式内——判定式管的是均值差；这条归因登记为**可推翻的读数口径**（推翻条件：锚点样本量上去后 judge 噪声上界显著抬高，或出现「同输入重生成」对照组以直接隔离生成方差）。

### 4.4 judge 噪声带实测（把 curve 3 的「≥7」升级为「9（n=4）」）

| 锚点 | n | 取值 | 极差 | 含义 |
|---|---|---|---|---|
| A1 | 4 | 100 / 100 / 99 / 100 | **1.0** | 顶格锚点几乎不抖（唯一一次 99） |
| A2 | 4 | 77 / 84 / 81 / 86 | **9.0** | **纯 judge 噪声带 = 9 分**（curve 3 时 n=2 只测到 ≥7） |

**判读纪律**：此前登记的「逐卡 ±10 以内属噪声域」——本轮 n=4 实测把纯 judge 噪声带钉到 **9 分**，与之相符但更准；**逐卡的 ±10 仍不足以作能力结论**，因为逐卡分布的极差本身就到 21 分（生成方差叠加）。

完全静默约 25 分钟后重试，**仍然 100% 429** ⇒ 排除「本会话自身消耗配额」假设 ⇒ 判为**账号级当日配额耗尽**（当日 59 万 tokens）。同一天再等没有意义（配额按日重置）。

### 5.4 根因链（三层，逐层可验证）

1. **连发面**：judge 的**元验证段先于逐卡段**连发 6 次（2 锚点 + 4 反例）——只给逐卡段加延迟（`--card-delay-seconds 45`）**对元验证段无效**。
2. **重试语义**：客户端 429 退避 `retry_delays = (1.0, 3.0)`（`server/src/fde_api/ai/deepseek.py:400`，有 `Retry-After` 则按供应商语义）——1s/3s 的重试**只会把限流窗口继续撑住**，不构成退避。
3. **兜底（零生产改动）**：NEW `_ThrottledSession`（`scripts/diagnostic_eval/run_eval.py`）包住 judge 客户端的 HTTP session，**任意两次请求之间**强制最小间隔（CLI `--call-interval-seconds`，本轮实测 20s）。**只作用于评测进程，生产代码零改动**。

### 5.5 复核（兜底有效性）

15:1x 单次探针 ⇒ **HTTP 200**（配额窗口解除）。随后真机重跑，**节流代理下 12 次评分调用全部 succeeded**（ev3 重评分 `meta_gate=pass`；ev4 生成 6/6 ＋ ev4 评分 12 次调用全成功）⇒ **兜底有效，且不依赖「配额恰好恢复」**。

### 5.6 附带发现：批跑撞产品访客日限额（第二道闸）

ev4 首次生成失败在**另一道闸**：`diagnostics/service.py:177` 抛「今天的使用次数已达上限」——那是**产品自己的访客日限额**（`FDE_DIAGNOSTICS_DAILY_IP_LIMIT`，缺省 20/IP/日）。原因：批跑用**固定合成 IP**（`203.0.113.x`，按卡位取模），同一天多次批跑把同一批 IP 的日计数器顶满。
**兜底**：评测进程内抬阈值（`FDE_DIAGNOSTICS_DAILY_IP_LIMIT=200`）——**活体容器读自己的 env，访客侧行为零变化**。
**留痕**：这是「评测批跑与产品限流共用同一把闸」的固有耦合，后续轮宜把批跑 IP 改成按 run 派生（可推翻登记项 L-6）。
