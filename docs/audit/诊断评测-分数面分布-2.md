## 一、为什么消解条件按字面不可执行，以及怎么忠实执行

第十六轮注册的消解条件在 HEAD 代码上**字面不可执行**——三个机械事实：

1. **prompt-v1 文本已不存在**：`server/src/fde_api/diagnostics/prompts.py` 只含 v2（curve-3 断点 `5dbbe4b` 整体替换：R-4 条款对齐 number-gate-v2＋新增「重试修复」段；v1 文本只存于 git 历史）。
2. **数字闸 v2 无条件在位**：`report_contract.py::NUMBER_GATE_VERSION` 被当前 runner 无条件打进 run.json（`scripts/diagnostic_eval/run_eval.py:238`）——今天从 HEAD 产出的任何 run 组键必含 `number-gate-v2`。
3. **runner 无版本选择**：`run_eval.py:176` `prompt_version = diag_jobs.REPORT_PROMPT_VERSION`——常量即现状，无 CLI 旗标。

⇒ 在 HEAD 上「再跑两轮 prompt-v1」**必然产出 prompt-v2 的 run**；即便从 git 历史把 v1 文本手抄回 HEAD，产出的也是「旧提示词 × 新数字闸」的**嵌合体**——其四轴组键 ≠ 历史 v1 组键，按规则**不许混组**（混组=假分布，第十六轮 §二的边界）。

**忠实执行＝时间机复刻**：历史 v1 组唯一 run `2026-11-11`（2026-11-11 08:31 local 创建）生成于 #311 合并（08:20）之后、`5dbbe4b`（11:08）之前 ⇒ **`e96efa3` 就是它的生成树**。`git worktree add <tm> e96efa3 --detach` 从 git 历史整树复刻该管线状态，**用那棵树自己的 runner** 跑两轮。生成器与 judge 语义零触碰——复刻的忠实性不靠自觉，由组键机械保证（§2.3）。

## 五、判定的读法

- **三态语义**：`decidable`＝|Δ| 严格大于参与分布的较大极差且两组 n≥3；`within_noise`＝n 够但 Δ 落在噪声带内；`insufficient_data`＝n 不足，规则机械拒绝读数（不编造方向）。
- **本轮主读数**：评分面版本差在两张达 n≥3 的卡上**可读且均落 within_noise**——v1→v2 的评分面变化**无可判定的退化、也无可判定的提升**（Δ −2.0/−0.7，带 21/12）。
- **第十六轮的「看着像生成器变差」被推翻**：单样本 Δ（−6.3/−7.0/−5.0）在补到真样本后收敛到 −2.0/−0.7/−5.0(n=1)——insufficient_data 语义拦住的正是这种单样本假信号。
- **`within_noise` ≠「一样好」的强断言**：只是「当前样本量与噪声带下分辨不出」。同理 010 的 Δ=+11 虽超其带 5，但 v1 n=1 ⇒ 规则拒绝读数（不因超带就放行）。
- **与生成侧合读**（§六新发现）：v2 的真实收益在**生成侧合规**——v1 时代卡次死亡率 50%（11/22，含链二补样滚动）vs v2 时代 0/18；评分面等价＋生成面存活率翻倍＝「v2 换得值」的可判定依据，两者都是规则/机械计数输出，非主观评价。
- **somwyn/010/001 仍 insufficient_data**：somwyn 三连死于 v1 闸（§4.1 注²）是结构性现象（D1 归因），继续补 v1 滚动的边际收益递减；挂账见 §六。

- **L-9 时间机评测配方**（登记）：生成器版本升级时，旧版本组**必须在切换前补足 n≥3**，否则版本差永久不可判（本轮是事后补救：唯一可行路径＝从 git 历史整树复刻时代管线）。配方可复用：锁定旧版本提交 → detached worktree → era 自带 runner → harness-only 补丁（节流＋版本解耦）→ 组键机械归组。
