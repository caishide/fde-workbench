## 五、自动触发机制实况与工作流嵌入规范（为什么不能只靠模型「自觉调用」？）

### 5.1 底层触发机制实测事实

1. **宿主注入差异**：在 ZCode 宿主中，系统向模型注入的 `available-skills` 列表格式仅为 `- <skill-name> (file: <path>\SKILL.md)`，**不预注入 YAML `description` 字段**。在全局装有 290+ 技能的环境下，若外部提示词与工作流均未显式点名，模型仅凭英文技能名盲猜的自主触发率约为 **30%–50%**（软路由）。
2. **双宿主跨端补链已打通（ZCode ↔ Claude Code 100% 同构）**：原 `superpowers` 插件仅注册在 `~/.claude/plugins/`，导致 ZCode `Skill` 工具无法直接调用其中技能。现已自 MIT 上游 `obra/superpowers` 将 **`verification-before-completion`**、**`requesting-code-review`**、**`systematic-debugging`** 全局安装至 `~/.agents/skills/` 并软链至 `~/.zcode/skills/` 与 `~/.claude/skills/`——在 ZCode 与 Claude Code 双端统一使用裸名（如 `Skill(skill="verification-before-completion")`）即可 100% 原生调用。

### 5.2 两层工作流固化落点（把「软自觉」变为「流程必经关卡」）

1. **随仓主干工作流嵌入（已落盘 `.agents/skills/fde-delivery-flow/SKILL.md`）**：
   - 将 Top-12 核心质量技能直接嵌为 `fde-delivery-flow` 的必经步骤：
     - **Step 0–1（立项与实施）**：新架构/高敏开关先调 `strategy-red-team`；修缺陷/加门禁配合 `tdd`；遇跨进程/并发疑难调 `systematic-debugging`。
     - **Step 2（Push 前审查闸）**：非纯文档改动必调 `code-review`（≥3 文件或跨前后端加调 `requesting-code-review`）；触及多租户 `permissions.py` / 公网免注册写面 / 脱敏 / 结算 / 宿主通道 / `AGENTS.md` 红线必调 `intended-vs-implemented`。
     - **Step 3（本地实证闸）**：宣称完成或 push 前必调 `verification-before-completion`（涉桌面 UI 加调 `fde-gui-regression`）。
     - **Step 4 & 8（收尾与打包闸）**：发 PR 前调 `neat-freak` 现测口径与双份手册对齐；涉桌面交付物必调 `fde-package-verify`。
   - **效果**：日常只需触发一次 `/fde-delivery-flow`（或口头说「走交付流」），即链式拉起整套审查、证伪、实证与收尾闭环。
