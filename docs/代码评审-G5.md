### 保留的 findings（均已修复，随本轮提交进入 PR #24）

**[P2] DSH 路径的失败逃出错误分类，重试在一条受支持的部署形态上完全失效**

- 期望：来自 `analyze_docx_json` 的一切失败都要以 `KimiError` 或 `GuidanceContractError` 到达
  处理器的循环，否则重试策略无从分类。
- 违反执行：`dsh_enabled=True`（`config.py:53` 的一等部署形态）→ 模型返回散文而非 JSON
  → `structured_completion` 的 `_parse_json_object(value)`（`ai_server_client.py:278`）抛裸
  `json.JSONDecodeError` → `kimi.py:91-92` 只转 `DSHRuntimeError`，故该异常原样逃出 →
  既不匹配 `except KimiError` 也不匹配 `except GuidanceContractError`（`jobs.py:66,75`）
  → 落进兜底分类 `analysis_unexpected_error`，**零次重试**。
- 证据：`ai_server_client.py:277-280`（解析点与其下方紧邻的 `DSHRuntimeError("ai_output_invalid")`
  表明原意就是转分类）、`kimi.py:84-92`、`jobs.py:66-83`。
- 影响：本 PR 的招牌能力在一个受支持的部署形态上静默不存在；运维按
  `failure_code=ai_output_invalid` 监控时永远看不到这些失败。
- 驳斥尝试：兜底分支「吸收」了崩溃（行落 failed，不会卡住）——**吸收不是预防**：
  它吸收的是崩溃，丢失的是重试与分类。DSH 能否保证 JSON？不能：只有提示词约束与非空文本检查
  （`ai_server_client.py:194-196,274`）。测试能否覆盖？不能：`grep structured_completion` 在测试目录零命中，
  `test_guidance_retry.py` 整体替换了 `KimiFileClient`，DSH 分支无测试。
- 修复：`structured_completion` 把 `JSONDecodeError` 转成 `DSHRuntimeError("ai_output_invalid", retryable=True)`；
  同时把 `ControlServiceError`（模型未配置/密钥不可用/无权限——确定性配置问题）转成不可重试的
  `DSHRuntimeError`，此前它也会原样逃出。回归钉在 `test_ai_server_direct_fallback.py`（+2 例）。

**[P3] 重试耗尽文案会给不可重试的终态错误加上「请重新发起分析」**

- 期望：不可重试失败一次即败、绝不消耗重试额度，消息也不该劝用户重做无意义的事。
- 违反执行：第 1 次尝试抛可重试错误（`ai_rate_limited`）→ 第 2 次抛不可重试错误
  （`ai_authentication_failed`）→ `_exhausted_message(..., attempts=2)` 产出
  「AI 服务认证失败，请检查服务端配置。（已自动重试 1 次仍失败，请重新发起分析）」——
  让用户去重新发起一次注定同样失败的认证。
- 证据：`jobs.py:69-74`（原文无 retryable 区分）、`test_guidance_retry.py` 原先只覆盖「首次即不可重试」。
- 影响：补救建议错误；与本 PR 自己声明的规则矛盾。
- 驳斥尝试：句子在计数上准确（确实重试过 1 次）——但计数的准确不等于建议的正确，
  消息的职责是告诉用户下一步该做什么。
- 修复：`_exhausted_message` 增加 `retryable` 参数；终态错误不可重试时只说
  「（已自动重试 N 次仍失败）」，不加「请重新发起分析」。回归钉在 `test_guidance_retry.py`。

**[P3] 存储对象缺失被归入「未预期错误」**

- 期望：`source_missing` 家族正是为「预调研源文件不存在」准备的。
- 违反执行：版本行存在但存储对象已被删 → `open_stream` 抛 `StorageNotFoundError("object_not_found")`
  （`storage/local.py:274`；OSS 侧 `storage/oss.py:168`）→ 抛在循环内但既非 KimiError 也非
  GuidanceContractError → 兜底分类 `analysis_unexpected_error`。
- 影响：确定性的、用户可行动的状况被报成「未预期错误」，运维无法与真 bug 区分。
- 驳斥尝试：现实中少见 —— 但「少见」不是预防机制；通用消息说的是「检查文件后重新发起分析」，
  而这恰恰是代码在别处专门分出来的失败类别。
- 修复：循环内捕获 `StorageNotFoundError` → 专用码 `source_object_missing` + 「请重新上传后再发起分析」。

**[P3] 瞬时错误（限流/超时）无退避，重试额度几乎必然被浪费**

- 违反执行：第 1 次返回 429 → `ai_rate_limited`（可重试）→ 循环立即重发（毫秒级）
  → 第 2 次几乎必然再次 429。
- 证据：循环体内无任何等待（`jobs.py:53-85`）；仓库内已有退避先例（`tests/test_ai_reliability_backoff.py`）。
- 驳斥尝试：对 `ai_output_invalid`（本 PR 的主目标）立即重试是对的、任何 sleep 都是纯延迟——
  该反驳只对契约失败成立，而限流/超时走的是同一分支。
- 修复：`TRANSIENT_RETRY_CODES`（限流/超时/服务不可用）重试前退避 1 秒；
  契约失败不退避（概率问题立即重试更合适）。两向行为各有测试钉住。

**[P3] 本地 DOCX 解析失败被标成可重试，而它是字节的纯函数**

- 违反执行：`local_extract=True`（当前配置）→ 损坏/空文件 → 本地解析抛错
  → `KimiError("kimi_file_extract_failed", retryable=True)` → 重试再解析同一份字节 → 同样失败。
- 影响：浪费一次重试额度，且最终消息让用户「重新发起分析」——而同一文件重跑必然同样失败。
- 驳斥尝试：供应商侧提取失败（`kimi.py:79-82`）确属瞬时，不能一并改成不可重试——
  故按**失败来源**而非按失败码区分。
- 修复：本地解析失败（确定性）与存储读取失败（`OSError`，瞬时）分开：前者 `retryable=False`，
  后者保持 `True`；供应商侧提取失败保持可重试。`test_kimi_client.py` 原先钉住「可重试」，
  该断言在 G4 之前是**休眠契约**（无人消费 `retryable`），现已随本次评审改正并说明理由。

**[P3] 重复投递可对已终态分析二次调用 AI**

- 违反执行：处理器只跳过 `{ready, cancelled}`，不跳过 `failed`，且不取行锁。
- 驳斥尝试（为何当前不可达）：出箱事件按目标原子认领、Redis 队列只弹一次、
  `active_key` 保证同 (job_type, target_id) 只有一个活跃任务 —— **当前没有重复投递**。
  但一旦按上一条引入重排队/接管，该分支立刻变成真实缺陷。
- 修复：终态集合补上 `failed`（同一目标的重复投递不得覆盖已有结论），并加回归钉子。

**[P3] 「永不卡在 analyzing」的措辞超过了机制能保证的范围**

- 期望：注释与 CHANGELOG 声称分析不会卡在 analyzing。
- 事实：兜底分支只覆盖**异常**，不覆盖进程死亡（OOM/部署）；此时 outbox 事件已 `dispatched`、
  租约过期无人接管、`BackgroundJob.max_attempts`/`available_at` 无消费方 → 状态永远停在 analyzing。
- 驳斥尝试：有对账/重排队任务吗？全仓检索无。租约能救吗？只在 `run_job` 被再次调用时有效，
  而没有任何东西会再次调用它。
- 处理：措辞改为「异常路径下必落 failed」，进程死亡路径写入台账待立项（不在本 PR 修）。

**[P3] `python-docx` 声明下限低于样本生成器实际所需**

- `pyproject.toml` 声明 `>=1.1`，但 `_build_comments` 用到 1.2.0 才有的 `Document.add_comment`；
  `requirements.lock` 钉的是 1.2.0，CI 今天安全，但声明的兼容区间已是假话。
- 修复：下限提到 `>=1.2`。

**[P3] 未预期异常用例没钉住「任务本身仍为绿」**

- 用例直接调 `handle_presurvey_analysis`，只断言分析行；而任务终态由 `run_job` 决定
  （`jobs/worker.py:46-54`），这条约定没被钉住。
- 修复：用例改走 `run_job(job.id)`，并断言 `job.status == "succeeded"`。

**[P3] 每次尝试复用同一个 `X-Request-ID`**

- 上游若按该头去重，第二次尝试会拿回第一次的坏结果，重试被静默挫败（仓库内无代码依赖该假设，
  但 DSH 路径做对了：每次调用一个新的 `Idempotency-Key`）。
- 修复：请求号按尝试派生（`{job.id}:{attempts}`），并加「两次尝试请求号不同」的钉子。

### 丢弃的候选（驳斥成立）

- **「重试计数与消息可能说谎」**：尝试数每次尝试恰好 +1，`retries = attempts - 1` 恒等于实际重发次数；
  混合序列（先可重试、后不可重试）下计数依然准确。无法构造出消息说谎的执行 → 丢弃。
- **「重试打开同一 storage_key 会撞租约」**：本地存储的每键 `RLock` 只在流打开期间持有，
  关闭即释放；OSS 侧是无状态 `get_object`。→ 丢弃。
- **「重试前的会话状态会污染第二次尝试」**：session factory 设 `expire_on_commit=False`，
  且最后一次提交在进入循环前，循环内无未提交写入。→ 丢弃。
- **「任务绿而分析失败会让作业统计错乱」**：无消费者读 `BackgroundJob.status` 来判断分析成败，
  UI 直接轮询分析行。→ 丢弃。
- **「failure_code 分类边界破了」**：完整枚举了生产者侧全部码与全部消费者
  （`serialize_analysis` 不分支、桌面只按 `analysis_state` 分支、G3 场景矩阵只引用仍在产出的码），
  新增的 `analysis_unexpected_error` 对所有消费者都是通用处理。→ 丢弃。
- **「失败消息会泄漏文档内容」**：兜底消息是固定中文、日志只记异常类型；
  `GuidanceContractError.path` 在每个构造点都只由字段名与下标拼成。→ 丢弃。
